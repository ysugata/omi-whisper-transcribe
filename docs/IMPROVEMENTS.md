# 改善ロードマップ

2026-07-02 時点のコードベース調査（実データ分析込み）で洗い出した改善候補の一覧。
「対応済み」は本リポジトリに実装済み。「見送り」は調査の結果、現時点では
問題が実在しない・費用対効果が低い・実測が先、と判断したもので、判断根拠を残す。

## 調査で判明した実態（2026-07-02 実データ）

- レビューキュー: 1,465件滞留 / 消化22件。**93% (1,385件) が importance=低**、
  雑談・移動中メモ + 独り言・メモで 1,364件 → キュー投入基準の問題であり、レビュー UI の問題ではない
- フィードバックループ (`review_weights.json`) の実測修正率:
  RAG高類似度 **15%**（ほぼ直す必要なし）、外部音声混入 **86%**（ほぼ要修正）→ ポリシー化の根拠
- 用語補正辞書 392 エントリ（正解表記327語）のうち **322語が hotwords 未登録** → 同じ誤認識が再発し続ける構造
- LLM 提案キュー (pending_suggestions) は 0件、キーワード候補 99件は全て処理済み → 提案系の滞留はなし

## 対応済み

### 1. レビュー件数の削減（学習ループの効率化）— 最優先ペイン

| 項目 | 内容 |
|------|------|
| キュー投入ポリシー | RAG類似度 ≥ 0.8 は自動承認扱い（外部音声疑いは自動承認しない）、低重要度×雑談/独り言はスキップ。`queue_policy` で調整・無効化可能 |
| TV 混入ジャンクの扱い | 「低+雑談と分類済みの TV 混入」はレビュー価値なしとしてスキップ（エクスポートからも external_audio_max で除外済み）。`casual_keep_external_audio: true` で旧挙動に戻せる |
| 透明性 | 除外分は `/api/review/stats` の `total_raw` / `policy_excluded` で常に確認可能（黙って隠さない） |
| min_priority_score | スコア下限による追加絞り込み（デフォルト無効） |

実データでの効果: レビュー待ち **1,465件 → 85件**（重要セッション・低類似度 RAG・casual 以外の外部音声疑いのみが残る）。

### 2. 音声認識精度（誤認識を発生源で減らす）

| 項目 | 内容 |
|------|------|
| 用語辞書 → hotwords 自動連携 | `term_corrections.json` の正解表記をデコーダバイアスに自動投入。誤認識バリアント数が多い語（=慢性的に間違われる語）を優先 |
| 好循環 | 誤認識が減る → LLM 補正・辞書補正・レビューの対象自体が減る |
| 制約と対処 | hotword トークン予算は200（Whisper 448トークン窓の実測安全値）のため「全部入れる」は不可能 → 優先度付けで解決。`dictionary.max` で調整可 |

### 2.5 用語補正の破壊バグ修正（実データ検証で発見, 2026-07-02）

実データ検証中に、`term_corrector.correct()` の**盲目的部分文字列置換**と学習スナップショット由来の
一般語エントリ（`ログ→log`, `ラム→RAM`, `ライン→LINE` 等）の組み合わせで、
「プログラム→プlogRAM」「ガイドライン→ガイドLINE」「インスタントラーメン→Instagramントラーメン」
のような破壊が起きることを確認した。

- **保存データに実害なし**: 補正結果を transcript に書き戻す batch_corrector (sync) の経路は
  2026-05-25 導入で、最終録音 (2026-05-11) より後だったため。次の録音から破壊が始まる状態だった
- **修正**: 置換を語境界考慮型に変更（カタカナ語の前後がカタカナなら複合語とみなして置換しない。
  英数字パターンも同様）。term_corrector / suggestion_learner 共通
- **辞書クリーニング**: 恒等マッピング40件（`パソコン→パソコン` 等の無意味エントリ）と
  意味破壊トラップ4件（ラム/ログ/ライン/トークン）を削除（392→348エントリ）
- **残課題（ユーザー判断）**: 提案ループ由来の英語化エントリが79件残存
  （`デプロイ→deploy`, `キャッシュ→cache`, `エージェント→agent` 等）。境界修正後は安全だが、
  日本語として正しい語を英語表記に変える「スタイル選択」であり、誤認識修正ではない。
  不要なら Viewer の用語補正タブから削除可能。提案ループに一般語ガード
  (`_COMMON_LOANWORDS` 参照) を入れるのも将来課題

### 3. セキュリティ

- 管理 API (8091) のオプトイン・トークン認証 (`MANAGEMENT_TOKEN`)。Viewer プロキシへ自動配線。デフォルト無効で挙動不変

### 4. コード健全化

- 未使用 FTS5 テーブル/トリガーの削除（日本語は unicode61 でトークン化できず LIKE 検索が正; 書き込みオーバーヘッドのみ発生していた）
- 47カラムの `INSERT OR REPLACE` 3重複を `SESSION_UPSERT_SQL` + `Indexer.reindex_session()` に集約
- Bridge の未使用 `llm_corrector` インスタンス削除
- `should_run_stage_c` の docstring と実装の乖離修正

## 見送り（判断根拠付き）

### 精度関連

| 候補 | 判断 |
|------|------|
| ノイズ除去 (`NOISE_REDUCE_ENABLED`) のデフォルト有効化 | スペクトルゲーティングは静的環境では逆効果になり得る。効果は環境依存のため実測 (`tools/compare_*` で A/B) してから |
| `transcribe_audio` のハードコード信頼度閾値の env 化 | 現行値は実測チューニング済み。knob を増やすより、変える根拠が出た時に env 化する |
| initial_prompt の活用 | 論文リサーチ済み: 日本語精度に効果なし（プロジェクトメモリ参照）|
| kotoba-whisper 等モデル差し替え | 検証済み: hotwords 非対応で不適。large-v3 が現状最適 |
| 深夜バッチでの高精度再文字起こし (VibeVoice 9B で importance=高のみ再処理) | 有望だが VRAM 6.6GB/RTF コストが大きい。まず辞書→hotwords の効果を見てから判断 |

### レビュー/学習関連

| 候補 | 判断 |
|------|------|
| LLM 提案の自動昇格 (occurrences ≥ N で辞書へ自動追加) | pending_suggestions は現在 0件で滞留なし。suggestion_learner が既に ≥2回出現パターンを決定論的に自動適用しており、二重の仕組みは不要。滞留が再発したら実装 |
| キーワード候補の自動期限切れ | 99件すべて処理済み（滞留なし）のため不要 |
| 一括承認 API (bulk accept) | 投入ポリシーで根本解決したため不要と判断。DB を書き換えずポリシーで除外する方が可逆で安全 |
| レビューポリシーの Viewer 設定 UI | 頻繁に変える値ではない。まず JSON 直編集で運用し、需要があれば UI 化 |
| 自動承認分の RAG インデックス追加 | 人間が確認していないデータで RAG を強化するとエラーが自己増幅するリスク。承認済みのみ追加する現行設計を維持 |

### その他

| 候補 | 判断 |
|------|------|
| 全文検索の trigram FTS 化 | 現在 ~1,700 セッションでは LIKE で十分高速。1万件を超えたら SQLite trigram tokenizer で FTS5 を再導入 |
| 同時複数 WebSocket セッション対応 | 単一デバイス運用では未発生。マルチデバイス化する時に対応 |

## 運用メモ: 学習ループの回し方（推奨）

1. 日々: レビューキューは数十件レベルに保たれる。`A`/`E` でさばく（外部音声疑いと重要セッションが中心）
2. 誤認識に気づいたら: 用語補正タブに登録 → 次回から辞書補正 + hotwords バイアスが両方効く
3. 月次: Refiner 提案とキーワード候補を確認
4. しきい値調整: レビューが多すぎる/少なすぎると感じたら `queue_policy` の
   `auto_accept_rag_similarity`（下げると厳しく）や `casual_types` を調整
